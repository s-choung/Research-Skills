# 문서 작성 (한국어 문서, 리포트, 스펙)

ko-prose 본문은 문장 안의 문체를 다룬다. 이건 그 위 단계로, 무엇을 먼저 보여주고 무엇을 빼고 어떤 어휘로 잇는가를 다룬다.
출처: 정의근(EugeneChung)이 2022-2025년에 쓴 사내 문서, 광고 서빙 로직 배포 리포트의 LLM 초안 → 최종본 diff.

## 예시를 배경보다 먼저

- 설명 챕터 맨 앞에 실제 데이터에서 뽑은 예시를 놓고, 이후 설명이 전부 그 예시를 가리키게 한다.
- 예시는 지어내지 않고 실제 로그의 최빈 패턴을 고른다. 케이스마다 비율을 붙인다 ("입찰 요청의 약 75%").
- 형태만 중립적으로 보여준다. "필터링 1번", "AS-IS와 결과 동일" 같은 해설 주석과 처리 결과 컬럼은 넣지 않는다.
- 표는 Notion 표 대신 ASCII 박스 표 코드블록으로, 케이스 라벨 불릿 아래 들여쓰기.
- 용어 정의는 본문에 섞지 않고 예시 바로 아래 콜론 불릿으로 분리한다.
  - `slot : 지면. OpenRTB 스펙에서는 Imp`
  - `prefix : 입찰 요청에 포함된 정보는 아니고 TO-BE 로직에서 서빙할 때 생성하는 정보`

## 제목과 첫 줄

- 제목은 무엇이 언제 바뀌었는지를 평범한 말로. 티켓 번호와 구현 용어는 뺀다.

| 전 | 후 |
|---|---|
| SSP Imp별 Ad-Filtering + superset inference 배포 (TICKET-1234) | SSP 광고 서빙 로직 변경 2026-07-13 |

- 첫 줄에 관련 링크와 용어 대응 관계를 한 줄로. "관련: TICKET-1234, 배포 2026-07-13 17:50 KST / TO-BE 로직 = 마이그레이션 로직"
- 오래 남길 설명 문서는 첫 줄에 작성 시점을 적는다. "최초 작성 시점 : 2024년 11월 21일". 읽는 사람이 내용이 언제 기준인지 먼저 안다.

## TL;DR 은 수치가 아니라 현상으로

세 불릿 = 문제 / 바뀐 것 / 결과와 그렇게 판단한 근거.

| 전 (수치 나열) | 후 (현상 + 판단 근거) |
|---|---|
| 신규 경로 소진이 전일 대비 +35%로 대조군 경로(+11%)를 웃돌았다. 점유율 44% → 50% | TO-BE 로직 소진이 받는 트래픽에 걸맞은 수준으로 올라왔다. 변경이 없던 AS-IS 경로는 평소 수준으로만 움직였으므로 시장 상황이 아니라 배포 효과로 판단했다 |

설명 문서는 축이 다르다. 용어 정의 / 대응책마다 그게 왜 있는지 / 그래도 못 하는 것. 마지막 불릿에 한계를 놓는다.

```
- 무효 클릭 : OpenRTB 서버가 만든 click log URL 을 사람이 의도적으로 계속 접근하거나 프로그램으로 호출하는 경우
- 사전 필터링 : 광고주의 예산을 순식간에 소진할 정도의 대규모 공격성 클릭을 방어하기 위한 목적
- 사후 필터링 : 일반적으로 사람이 만들어내는 수준의 소규모 무효 클릭을 식별하기 위한 목적
- 인터넷에 공개한 웹 주소를 호출하면 클릭 로그가 발생하기 때문에 무효 클릭은 원천적으로 막을 수 없다!!
```

## 헤딩은 독자가 실제로 묻는 문장으로, 답은 헤딩에 붙인다

- 헤딩을 명사구로 만들지 말고 문의로 들어오는 문장 그대로 쓴다. "마우스 클릭만 클릭으로 인정하면 안 되나요?", "무효 클릭 로그는 누가 만드는가?"
- 답이 짧으면 물음표 뒤에 바로 붙인다. 목차만 훑어도 답이 나온다.

| 전 | 후 |
|---|---|
| 사전 무효 클릭의 광고 성과 영향 | 사전 무효 클릭은 광고 성과에 영향을 미치는가? NO |
| 사후 무효 클릭의 광고 성과 영향 | 사후 무효 클릭은 광고 성과에 영향을 미치는가? 예산 소진 |

- 나란히 놓고 비교하는 두 대상은 같은 축을 같은 순서로 쓴다. 사전 필터링과 사후 필터링을 판별 시간, 비용, 예산 소진, 오탐 복구 순서로 각각 적으면 독자가 표 없이도 대조한다.

## 케이스는 조합을 전부 나열하고 "즉" 한 줄로 닫는다

결론을 먼저 주장하지 않고 가능한 경우를 다 적는다. 독자가 스스로 결론에 닿은 다음 "즉" 문장으로 확인한다.

```
- 노출 웹 주소 열기 → 유효 노출 웹 주소 열기 → 클릭 주소 열기 : 노출, 유효 노출, 클릭
- 노출 웹 주소 열기 → 클릭 주소 열기 : 노출, 클릭
- 유효 노출 웹 주소 열기 → 클릭 주소 열기 : 유효 노출, 클릭
- 클릭 주소 열기 : 클릭
- 즉, 캠페인의 유효 노출 로그가 없어도 클릭 로그가 발생할 수 있습니다.
```

- 형식은 `조건 → 조건 : 결과`. 케이스마다 해설을 붙이지 않는다.
- 동작 순서도 화살표로 잇는다. "클릭 로그가 1개 발생합니다. → 랜딩 페이지 주소를 넘겨줍니다. → 랜딩 페이지를 엽니다."
- 정의는 백틱으로 감싸 본문과 분리한다. "광고 클릭은 `광고에 매핑된 웹 주소를 방문하는 것` 입니다."
- 독자가 가져갈 결론 문장에만 밑줄과 볼드를 준다. 한 섹션에 하나면 충분하다.

## 한계와 불가능은 완곡하게 쓰지 않는다

못 하는 것을 문서에서 가장 단호하게 적는다. 완곡어법은 "그럼 언젠가 되는 거냐"는 후속 문의를 만든다.

| 전 | 후 |
|---|---|
| 완전한 차단은 어려운 부분이 있습니다 | 무효 클릭은 원천적으로 막을 수 없다!! |
| 기술 검토가 필요한 사안입니다 | 기술적으로 가능하지만 현실적으로 불가능합니다 |
| 데이터가 적을 때는 해석에 주의가 필요합니다 | 즉, 유효 노출이 너무 작으면 어쩔 수 없습니다 |

- 불가능하다고만 쓰지 말고 왜 안 하는지를 비용으로 한 줄 붙인다. "정상 클릭 구분하려다 회사가 망합니다."
- 대신 뭘 하고 있는지는 별도 섹션으로 뺀다. 한계 문장에 "다만" 을 달아 흐리지 않는다.

## 불릿 구성

- 한 불릿 = 한 주장. 근거, 예외, 수치는 하위 불릿으로 내린다.
- 흐름: 구조 → AS-IS 동작 → 정상 케이스 → **그러나** 문제 케이스 → **즉** 한 줄 결론.
- 번호 목록에 볼드 제목을 얹는 형식("1. **imp별 ad-filter 요청**: …")은 쓰지 않는다. 평서 불릿과 들여쓰기로 푼다.
- 문제는 내부 동작이 아니라 독자가 겪는 결과로 서술한다.

| 전 (내부 동작) | 후 (독자가 겪는 결과) |
|---|---|
| 첫 지면 기준으로 거른 결과를 재사용한다 | 1번 지면에만 나갈 수 있는 광고가 나머지 4개 지면에도 나갈 수 있다 |
| 203과 210 bid loss 가 사라진다 | 지면에 맞지 않는 광고가 노출되던 문제가 사라졌다 |

- 변경의 효과는 독자 이득까지 한 불릿 더. "각 지면 입장에서는 전보다 넓어진 후보 중에서 고르게 되므로, 더 좋은 광고가 나갈 수 있다."

## 어휘

- 문서를 관통하는 축을 정하고 그 용어로 통일한다. AS-IS / TO-BE 축이면 구현체 이름("기존 inference-server", "node-dsp-skeleton")은 쓰지 않는다.
- 본문 어휘 = 예시 어휘. 예시 표에 없는 필드는 사실이 정확해도 언급하지 않는다.
- 용어 선택 기준은 표준 정확성이 아니라 독자의 오독 가능성. imp 가 OpenRTB 표준이어도 광고 문서에서 impression 으로 읽히면 slot 을 쓴다. 표 컬럼은 영문, 본문은 한국어, 첫 등장에서 "지면(slot)"으로 한 번만 연결한다.

## 수치

- 서술문에서는 반올림하거나 범위로. 정확한 값은 표에 둔다.

| 전 | 후 |
|---|---|
| 99.6 → 110.1 로 약 11% 늘었다 | 약 90개에서 110개 이상으로 늘었다 |

- 표에는 사람 판단을 적는 비고 열을 둔다. "배포 후 10배", "이탈", "하락 지속", "배포 후 신규(다른 매체에서 이관)".
- 내부 지표만 보여주는 표는 독자가 아는 단위의 표로 바꾼다 (경로별 소진 → 광고주별 소진).
- 효과를 주장할 때는 변경이 없던 쪽을 대조군으로 세우고, 그래서 배포 효과로 판단했다고 문장으로 적는다.

## 빼는 것

- 발견 경위와 작업 서사 ("DSP 서버 migration 하던 중 파악했다")
- 내부 구현 이름 (xxhash, candidate_key, BidPostProcessor)
- 본론과 다른 얘기를 하는 괄호 보충 ("(자사 위젯 지면은 원래부터 …)")
- 근거 없는 수식어 ("속성이 다른")
- 일어나지 않을 오해에 대한 방어 문장, 대안 나열
- 링크한 문서에 이미 있는 설명: 링크가 설명을 대신한다

## 종결어미

- 리포트, 기술 스펙, 태스크 문서: 평서체 ("…였다", "…한다", "…해야 한다")
- 팀에 설명하는 공유 문서, PR 답글: "…합니다"
- Self report: 명사형 종결도 섞는다 ("…제거 가능", "…확인함")

## 문서 유형별 골격

- **변경 공유 리포트**: 제목(무엇이 언제) / 관련 링크 한 줄 / TL;DR 3불릿 / 예시 / 배경과 문제(AS-IS) / 변경 내용(TO-BE) / 결과 데이터
- **기술 스펙**: 요약 / 배경 / 목표 / 계획(코드 위치, 핵심 클래스 시그니처, 사용 방법, 출력 형식) / 이외 고려 사항(성능 영향, 확장 가능성, 대안 검토 표) / 후속 작업 체크박스
- **시스템 설명 문서**: 헤딩을 실제 테이블과 아티팩트 이름으로 단다 (`feature_daily.user_app_summary`). 각 헤딩 아래에 무엇을 만드는지, 어떤 조건에서 동작하는지, 코드 위치 permalink, 그대로 실행 가능한 Example SQL.
- **태스크 문서**: 작업 설명 불릿 / 하위 작업 체크박스. 확인에 쓴 curl 명령과 응답 JSON 을 그대로 붙인다. 안 할 일도 이유와 함께 적는다 ("일단은 phase 1으로 충분하다고 보고 있다. 만약 예외 상황들이 계속 나오면 추진한다").
- **Self report**: Overview / Performance Highlights(항목마다 weight) / Roles and Performances / Raw Data(PR과 Jira 검색 링크). 성과는 비용과 시간의 전후 숫자로 ("일 $210 에서 $100 수준으로 낮췄다").
- **개념 설명 문서 (반복 문의 대응)**: 사업팀과 support 가 같은 질문을 계속 보낼 때 쓴다. 작성 시점 한 줄 / TL;DR callout(정의, 대응책, 한계) / 실물 예시와 스크린샷 / 문의 질문을 그대로 단 헤딩들 / 오탐 사례 / 모니터링 대시보드 링크 / 발전 역사.
  - 실물은 축약하지 않고 그대로 붙인다. 클릭 URL 전문, 브라우저 주소창 스크린샷처럼 독자가 직접 확인할 수 있는 형태여야 설명이 통한다.
  - 발전 역사는 분기 단위로 링크만 남긴다. `2023년 2Q : <문서 링크>`.

## 링크

- 근거는 링크로 대신하고 설명을 옮겨 적지 않는다.
- 코드는 커밋 해시가 박힌 permalink 로 걸고, 본문에 "코드 위치 : <링크>" 형태로 붙인다.
- 문서의 상세도 상한을 문서 안에 적어 둔다. "본 문서에서 너무 자세하게 설명하지 않으려고 합니다. 최대한 간단하게 설명하고 관련 SUPPORT 이슈를 연결해두겠습니다." 이후 사례가 늘어도 문서가 안 부푼다.
- 반복 문의는 티켓 링크를 걸고 "위의 설명을 이해하셨다면 당연하다는 걸 이해하실 수 있습니다" 로 닫는다. 티켓마다 설명을 다시 쓰지 않고 문서가 답변을 대신한다.
