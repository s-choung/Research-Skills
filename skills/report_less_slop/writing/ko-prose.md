
# ko-prose: 한국어 글 AI체 제거

한국어 콘텐츠에서 정보만 남기고 연출, 판정, 의인화, 직역, 메타포를 뺀다.
영어 전용 `stop-slop`과 `humanizer`의 한국어판. **영어 산문이면 그 둘을, 한국어면 이걸 쓴다.**

문서, 리포트, 스펙, PR 본문처럼 여러 문단짜리 글을 통째로 쓸 때는 [doc-style.md](doc-style.md) 를 같이 읽는다.
이 파일은 문장 안의 문체를 다룬다. doc-style.md 는 그 위 단계로, 무엇을 먼저 보여주고 무엇을 빼고 어떤 어휘로 잇는가를 다룬다.

## 1. 진행자 멘트, 자평, 중요도 과장

자료가 스스로 "중요해 / 똑똑해 / 이게 주제야"라고 말하는 문장. 정보 0, 연출만.

**진행자 메타 선언**
- ✘ "이게 오늘의 주제다", "오늘의 핵심이다", "핵심 선언:", "다음 절의 주제다", "오늘 다루는 / 오늘 발표는"

**자평 (자기 칭찬과 판정)**
- ✘ "영리한 우회법", "이 방식이 왜 똑똑한가", "흥미로운 겹침", "뼈아픈 비용", "X가 중요하다"
- ✘ "핵심 발견 / 핵심 가정 / 핵심 난제"의 수식어 "핵심"
- 일반화: 똑똑하다 / 영리하다 / 흥미롭다 / 중요하다 류 전부

**중요도 과장 (판돈 올리기)**
- ✘ "이 질문의 답이 오늘 전부다", "오늘 가장 중요한 X", "여기서부터가 핵심"

고치는 법(정보만 남김):

| 전 | 후 |
|---|---|
| 영리한 우회법 | 우회법 |
| 정확히 짚는 게 중요하다. 자주 잘못 설명된다 | 자주 잘못 설명된다 |
| 핵심 발견: | 발견: |
| 이 질문의 답이 오늘 전부다 | (삭제) |

절 간 연결: 산문 선언("다음은 X를 다룬다") 대신 `(§N)` 참조.

## 2. 영어 직역 AI체와 의인화

영어 표현을 한국어 단어로 1:1 매핑한 문장. 한국어 화자가 실제로 안 씀.

실제 거부 사례:

| 전 (직역) | 후 |
|---|---|
| 살아 있는 사례 (live examples) | 실사용 사례 / 실제 사례 / 사내 사례 |
| 굴러가는 도구 (running tools) | 돌아가는 도구 / 운영 중인 도구 / 사내 사용 중 도구 |
| validator 배선 완료 (wire up) | validator 연결 완료 / 등록 완료 |

매핑:
- running → 돌아가는 / 운영 중인 / 쓰고 있는 / 사내 사용 중
- live → 실사용 / 실제 / 사내
- in production → 운영 중 / 실제 사용 중
- wire up → 연결 / 등록 (배선 ✘, 전기 배선 비유라 SW에 안 씀)

**의인화 동사 금지**: 시스템, 도구, 서비스를 주어로 "살다 / 숨쉬다 / 굴러가다".

새 표현 내기 전 자문: **"한국인이 실제로 이렇게 말하나?"** 의심스러우면 사용자에게 물어봄.

## 3. 구어 메타포 동사 → 서술형 압축

구어체 메타포 동사를 빼고 평이한 명사 중심 서술로.

실제 시연 사례:

| 전 (구어 메타포) | 후 (서술형) |
|---|---|
| 숫자를 만지는 상시 비용을 깐다 | counting 비용이 상시로 발생한다 |
| 코어를 더 먹는다 | 코어를 추가로 쓴다 |
| 허깨비가 된다 | 이미 돌려준 자리를 가리키게 된다(dangling) |

금지 동사 류: 깐다 / 먹는다 / 만진다 / 허깨비 같은 구어 메타포.
같은 목록과 문단 안에서는 문장 형태를 통일한다.

## 4. 표준 영어 기술용어는 인라인 유지 (번역하지 마라)

이미 도입한 표준 용어는 억지 한글 번역 금지. counting, tracing, Garbage, dangling, ring, Root 등은 그대로 인라인. 단 **처음 나올 때 주변 산문으로 풀어 설명**.

예: ✘ 뿌리 → ✓ Root (GC root set, 트리 root)

"jargon 금지, 풀어서 설명" 규칙과 충돌하지 않는다: 용어 라벨은 영어로 두되 설명을 산문으로 푼다. 제거 대상은 메타포와 구어체뿐, 표준 용어 라벨이 아님.

**코드와 설정에 그대로 있는 이름(고유명사)은 번역 자체가 오류다.** 표준 용어보다 더 엄격하다.

설정 키, 컬럼명, 테이블명, 메서드/태스크명처럼 코드나 설정에 그 철자 그대로 존재하는 이름은 한글로 옮기지 않는다. 옮기면 독자가 "이 한글이 코드의 무엇이냐"를 되짚어야 하고, 실제로 "그거 X 맞죠?"라고 되묻게 된다.

실제 거부 사례(설정 키 `imp_channel` 을 "노출 채널"로 직역):

| 전 (직역) | 후 |
|---|---|
| 노출 채널 조회 시작 시간 | `imp_channel` 조회 시작 시간 |

리뷰어가 "노출 채널 = imp channel 인거죠?"라고 되물었다. 직역이 코드의 어느 이름을 가리키는지 다시 확인하게 만든 것이다.

규칙: 코드에 `imp_channel` / `has_view` / `merged_bid_log` 로 있으면 그 이름 그대로 쓴다. 풀어 설명하려면 이름은 두고 괄호로 덧붙인다. `imp_channel`(노출 로그 채널) 식이다. 한글로 갈음하지 않는다.

**동작을 가리키는 표준 용어를 한국어 동사로 활용하지 마라.** 명사 라벨보다 눈에 덜 띈다.

`fold`, `flush`, `spill`, `drain`, `hydrate` 처럼 동작 이름인 표준 용어에 한국어 어미를 붙이면 번역인지 비유인지 구분이 안 되고, 읽는 사람이 "접는 게 뭐냐"고 되묻는다.

| 전 (동사 활용 직역) | 후 |
|---|---|
| NULL 원소를 0 으로 접는다 (fold) | NULL 금액을 0 으로 처리한다 |
| 버퍼를 흘려보낸다 (flush) | 버퍼를 비운다 |
| 메모리가 넘쳐 디스크로 흘린다 (spill) | 디스크로 `spill` 한다 |

고르는 법: 그 동작을 평이한 한국어로 적을 수 있으면 그렇게 적고(접는다 → 처리한다), 동작 자체가 표준 용어로 굳었으면 원어를 그대로 쓴다(`spill` 한다). 금지 대상은 그 사이의 직역 활용형뿐이다.

출처: PR 본문 교정 사례. `reduce` 를 "접는다"로 옮겼다가 되물음을 받았다.

## 5. 추가 AI 패턴 (humanizer 보강, 한국어에도 적용)

- **3개 나열 습관**: 운율 맞추려 무조건 셋. ✘ "빠르고 안전하고 강력한", "혁신, 영감, 통찰". 실제 항목 수만큼만. 둘이면 둘.
- **아부체 / 굽신 톤** (채팅 답변): ✘ "좋은 질문이에요!", "정확히 짚으셨습니다", "훌륭한 지적입니다". → 본론 바로.
- **동의어 돌려쓰기**: 같은 대상을 매번 다른 말로. ✘ "참조 세기 … 레퍼런스 카운트 … 횟수 집계"를 한 문단서 번갈아. → 한 용어로 고정(§4와 같은 방향).
- **빈 수식과 홍보체**: ✘ "혁신적인", "강력한", "획기적인", "원활하게". 측정하거나 근거를 대지 못하면 삭제.
- **추측 메우기**: 근거 없이 ✘ "그런 것으로 보인다", "아마 그랬을 것이다", "전문가들은 이렇게 말한다". 출처 있으면 명시, 없으면 "자료에 없음" 또는 절 삭제.
- **물결표(~)**: 자리 표시로도 범위로도 쓰지 않는다. ✘ "~가 중요하다" → "X가 중요하다". ✘ "2022~2025" → "2022-2025" 또는 "2022년부터 2025년까지".

## 6. 통계와 ML 한정 용어를 일반 의미로 끌어다 쓰지 마라

좁은 학술 의미가 있는 단어를 소프트웨어 일반 상황에 jargon으로 가져다 쓰는 습관. 원래 의미로 쓰는 자리가 아니면 **무엇이 같고 무엇이 달라졌는지 평이하게 풀어 서술**한다.

- **회귀 / regression**: 회귀 분석과 회귀 모델을 가리킬 때만 쓴다. 코드 변경으로 동작이 "예전으로 되돌아갔다 / 기능이 깨졌다 / 문제가 재발했다 / 장애가 복구됐다"는 뜻으로는 쓰지 않는다.
- **보간 / interpolation**: 알려진 두 값 사이를 수식으로 계산해 채울 때만 쓴다. 빈칸을 기본값이나 직전 값으로 메우는 건 보간이 아니다.
- **수렴 / converge**: 반복 계산이 한 값에 가까워지는 것. 의견이 모이거나 수치가 안정된 상태에는 쓰지 않는다.
- **유의미하다 / significant**: 통계 검정을 실제로 돌렸을 때만 쓴다. 차이가 크다는 뜻이면 얼마나 큰지를 적는다.

| 전 (jargon 오용) | 후 (평이 서술) |
|---|---|
| 이번 변경으로 회귀가 발생했다 | 이번 변경 뒤 X 동작이 예전 결과로 다시 바뀌었다 |
| 회귀 검증 / regression 검증 | 기존 동작이 그대로인지 비교해 확인 |
| regression 신호 | 이전과 달라진 부분이 있다는 신호 |
| 결측 구간을 보간했다 | 결측 구간을 직전 값으로 채웠다 |
| 논의가 수렴했다 | 논의가 한 안으로 정리됐다 |
| 유의미한 개선이 있었다 | p50 응답이 120ms에서 40ms로 줄었다 |

출처: 팀 한국어 용어 가이드(원칙, 공통 치환표, 리뷰 체크리스트).

## 7. 반론을 부정형으로 되받는 장황한 결론 → 짧은 직접 결론

리뷰 답글에서 흔하다. 앞 절이 메커니즘과 근거를 이미 말했으면, 결론을 상대 반론의 부정형("X를 새로 만들지/일으키지 않습니다", "깨지지 않습니다", "문제를 일으키지 않습니다")으로 되풀이하지 않는다. 짧은 직접 결론으로 끝낸다. 앞 절과 중복이라 줄여도 내용 손실이 아니다(작업 방식 "손실 0"의 예외).

| 전 (부정형 되풀이) | 후 (직접 결론) |
|---|---|
| 두 경로를 맞추는 것이라 불일치를 새로 만들지 않습니다 | 두 경로를 맞추는 것이라 문제없습니다 |
| 기존 동작을 그대로 보존하므로 깨지지 않습니다 | 기존 동작을 그대로 보존하므로 안전합니다 |

판단: 앞 절이 근거를 말했나? 말했으면 결론 절의 부정형은 중복 → 짧게. 근거가 그 문장에만 있으면 유지.

출처: 코드 리뷰 답글 교정 사례.

## 8. 설명과 요약을 새로 쓸 땐 핵심만: 등가물은 참조로, 메커니즘 재서술 금지

기존 산문을 **다듬는** 게 아니라 **설명과 요약을 새로 생성**할 때는 결론과 핵심부터 쓰고 부연은 요청받을 때만 붙인다. 아래 작업 방식의 "손실 0"은 편집과 번역에만 적용된다. 핵심 = **무엇을 하나 + 왜 필수/무슨 결과**. 나머지는 뺀다.

- **등가물 참조로 메커니즘 대체**: 이미 있는 함수, 기존 동작, 표준 패턴과 같으면 "X와 동일"로 가리키고 절차(조건 분기와 중간 단계)를 재서술하지 않는다. 독자가 그 등가물을 알거나 코드로 확인 가능하면 참조 한 줄이 낫다.
- **부연 생략**: 코드와 맥락에서 확인되고 결론을 안 바꾸는 곁가지(순서 aside, 하위 함의, 내부 상수명)는 뺀다.

실제 시연(origin_item_id remap 설명):

| 전 (메커니즘 5문장) | 후 (핵심 2문장) |
|---|---|
| `origin_item_id`는 `_apply_filter`가 내부 소비… pool에 없고 origin만 있으면 원본 후보 찾아 스코어 재사용… item_id를 product로 remap해 반환… remap이 postproc보다 앞… dsp는 remap된 값 수신… `_CONSUMED_KEYS`라 bag 제외 | `AdFilterService.convertOriginItem`과 동일하게 remap 수행. remapped item_id로 추론하므로 반드시 필요. |

판단: 등가물로 가리킬 수 있나 → 참조. 부연이 결론을 바꾸나 → 아니면 삭제. 원저자 글을 보존하는 다듬기와 압축하는 생성 요약은 다른 모드다.

출처: remap 로직 설명 압축 사례.

## 9. 가운뎃점(·)으로 항목을 나열하지 마라: 2개는 "와/과", 3개 이상은 쉼표

항목을 가운뎃점으로 이어 붙이는 건 격식체 문어의 버릇이다. 개수대로 자연스럽게 잇는다.

- 2개: `와` 또는 `과`로 잇는다.
- 3개 이상: 쉼표(`,`)로 나열한다.

| 전 | 후 |
|---|---|
| 크기·속성이 다른 지면 | 크기와 속성이 다른 지면 |
| SSP_A·SSP_B | SSP_A와 SSP_B |
| 연출·판정·직역·메타포 | 연출, 판정, 직역, 메타포 |

예외: 코드나 설정에 그 철자대로 있는 고유명사의 일부와 슬래시 `/` 로 굳어진 표기는 대상이 아니다. 값이 딸린 절을 이어 붙였으면("`model-a` +11%·`model-b` −1%") 가운뎃점을 빼고 자연스러운 절로 푼다. "`model-a`는 +11%, `model-b`는 −1%"처럼.

출처: 공유 문서 가운뎃점 나열 교정 사례.

## 10. 부연 설명과 edge case로 분량 채우지 마라

가장 자주 나오는 패턴이다. 문체가 아니라 **양**의 문제라 §1부터 §9까지 다 통과해도 남는다.
판단 기준 한 줄: **이 문장이 없으면 읽는 사람이 다른 결정을 하나?** 아니면 삭제.

### 10-1. 앞 절이 이미 말한 근거를 불릿에 다시 붙이기

| 전 | 후 |
|---|---|
| 상시 차단 후보가 270칸 중 22.1%, 약 60칸을 점유한다. 이 슬롯은 매 요청 확정적으로 버려진다. 앞 150칸은 shuffle 대상이 아니라 같은 후보가 매번 그대로 다시 들어가므로 학습이 그대로 재현된다. | 상시 차단 후보가 270칸 중 22.1%, 약 60칸을 점유한다. 이 슬롯은 매 요청 확정적으로 버려진다. |

뒷문장은 바로 위 "위치별 통과율" 절이 표까지 붙여 이미 말한 내용이었다.
같은 문서 안에서 근거를 두 번 대지 않는다.

### 10-2. 코드 내부 조건을 산문으로 옮겨 답을 대신하기

질문은 "이 메모리가 의미가 있나"였는데 답에 이런 문단이 붙었다:

> 요청 의존 후보 46.2%는 확정 대상이 아니다. `record()`가 관측이 전부 차단일 때만 확정하므로,
> 통과가 한 번이라도 관측되면 빠진다. 과차단 위험이 여기서 닫힌다.

두 번 "무슨 말인지 모르겠다"는 지적을 받고 통째로 삭제했다. 구현 조건을 그대로 옮겨 적었을 뿐
질문에 답하지 않는다. 코드를 읽으면 나오는 내용을 산문으로 중계하지 않는다.

### 10-3. 측정하지 않은 수치를 시나리오로 만들기

> 시나리오 B: 차단분을 전부 알면 270칸이 전부 통과 후보로 채워짐 → kept 270 (+120%)

실측 후 156개로 정정했다. 확정 규칙상 성립조차 불가능한 시나리오였다.
근거 없는 수치는 범위, 상한, 시나리오 어느 형태로도 쓰지 않는다.

### 10-4. 결론을 바꾸지 않는 한정 나열

"측정의 한계" 4개 중 수치를 실제로 흔드는 건 "상시 차단 26.1%에 우연히 잡힌 키가 섞인다" 하나였다.
나머지는 삭제 대상:

- ✘ "1시간 단일 구간 측정이다": 그래서 뭘 다르게 하라는 건지가 없다
- ✘ "검증 지표는 A와 B를 같이 본다": 물어보지 않은 운영 절차

남길 한정이면 문장에 끼우지 말고 하위 목록으로 내린다. "A로 하되 B도 가능하고 C 경우는 예외다"가
아니라 "A로 한다." 아래에 `- 대안: B`, `- 예외: C인 경우`.

### 10-5. 편집한 뒤 편집 내용을 다시 설명하기

불릿을 지우고 나서 "세 번째 불릿에서 말하려던 X는 질문 2의 Y와 같은 내용이라 뺐습니다"를 덧붙였다.
diff에 다 보이는 내용이다. 고쳤으면 고쳤다고만 하고 끝낸다.

### 10-6. 줄표(—)로 문장 잇기

한국어에서 줄표는 드물게 쓴다. 자주 나오면 영어 글쓰기 습관을 옮긴 것이고(§2), 실제로 쓰이는
자리를 보면 "한 마디 더"를 붙이는 접착제다. 문장이 끝났는데 줄표로 이었다면 뒤에 붙은 절이
10-1부터 10-5 중 하나일 확률이 높다.

| 전 | 후 |
|---|---|
| 한 곳에 둔다 — 옮기면 낡는다 | 한 곳에 둔다. 옮기면 낡는다 |
| 억지 한글 번역 금지 — counting, tracing 등 | 억지 한글 번역 금지. counting, tracing 등이 해당한다 |

붙은 절이 필요한지 먼저 본다. 필요 없으면 삭제하고, 필요하면 마침표로 끊거나 쉼표로 잇는다.
라벨과 설명을 가르는 자리면 콜론을 쓴다(`배경: 로그인이 느리다`).

### 10-7. 괄호로 부연 밀어넣기

한 문장에 괄호 부연은 1개까지. 둘 이상이면 문장을 나눈다. 줄표를 막으면 부연이 괄호로 옮겨가므로
같이 건다.

| 전 | 후 |
|---|---|
| 검사(자동(닷새)) 결과 | 닷새 자동 계측 결과 |

출처: 티켓 코멘트 3회 축약. 10-6과 10-7은 프론트엔드 팀의 문장 규칙에서 가져왔다.

## 11. 문어체 한자어를 일상어로

공문서투 한자어는 정보를 더 주지 않으면서 문장만 굳힌다.

| 전 | 후 |
|---|---|
| 금번 작업은 상기 사유로 지연 | 이번 작업은 위 이유로 늦어짐 |
| 명일 배포 예정 | 내일 배포한다 |
| 오류 발생 시 재시도 | 오류가 나면 재시도한다 |

출처: 쉬운 공문서 쓰기 길잡이(국립국어원, 2022), 프론트엔드 팀 문장 규칙.

## 과잉교정 금지 (유지할 것)

다음은 평가가 아니라 **내용**이므로 건드리지 마라:
- 기술적 대비와 결론: "A가 아니라 B다". 예를 들어 "참조 세기가 아니라 tracing이 수거한다". 빈 수사인 "단순한 X가 아니라 진정한 Y"만 금지하고, 측정 가능한 대비는 유지한다.
- 측정 기반 결론 (실측 수치, 재현 결과)
- 표준 영어 기술용어 라벨
- 배경과 기각한 대안. 없으면 읽는 사람이 판단 근거를 못 읽는다. §10의 삭제 규칙보다 우선한다.
- 한계를 못 박는 단정과 그 근거. "무효 클릭은 원천적으로 막을 수 없다!!", "정상 클릭 구분하려다 회사가 망합니다" 는 §1의 중요도 과장이 아니라 결론이다. 완곡하게 바꾸면 "그럼 언젠가 되는 거냐"는 후속 문의가 늘어난다.

## 작업 방식 (편집 시)

1. **지우지 말고 고쳐 쓴다.** 원문이 담은 정보는 다 살린다. 5문단이면 5문단. AI체만 빼고 내용 손실 0.
2. **초안 → 점검 → 확정** 루프. 초안 쓰고 아래 점검 돌린 뒤 확정.
3. 사용자가 같은 파일을 실시간으로 직접 편집할 수 있다. **편집 전 항상 현재 바이트를 다시 읽을 것.**

## 출력 전 빠른 점검

- 문장이 정보냐 선언/판정이냐? 선언이나 판정이면 삭제.
- "중요하다 / 핵심 / 똑똑하다 / 영리하다 / 흥미롭다" 있나? 삭제.
- "이게 전부 / 가장 중요한 / 여기서부터" 판돈 올리기 있나? 삭제.
- 결론을 반론의 부정형("X를 만들지/일으키지 않습니다")으로 되받았나? 앞 절이 근거를 말했으면 짧은 직접 결론으로.
- 영어 직역 의심? "한국인이 이렇게 말하나?" 자문.
- "배선"(wire up) 등 직역 메타포? 연결 / 등록으로.
- 시스템이 주어로 살다 / 먹다 / 굴러가다? 평이 동사로.
- 구어 메타포 동사(깐다 / 먹는다 / 만진다)? 서술형으로.
- 무조건 3개 나열? 실제 수만큼.
- 가운뎃점(·)으로 항목을 나열했나? 2개는 와/과, 3개 이상은 쉼표로.
- 아부체("좋은 질문")? 본론 바로.
- 같은 대상 동의어 돌려쓰기? 한 용어 고정.
- 표준 영어 용어를 억지 한글 번역? 인라인 영어로 되돌림.
- 코드와 설정에 그대로 있는 이름(`imp_channel` 같은 설정 키, 컬럼, 테이블, 메서드명)을 한글로 번역? 식별자 원형으로 되돌림.
- 동작을 가리키는 표준 용어(fold / flush / spill)를 한국어 동사로 활용했나? 평이 동사나 원어로.
- "회귀 / 보간 / 수렴 / 유의미"를 통계와 ML 의미가 아닌데 썼나? 무엇이 같고 달라졌는지 평이 서술로 교체.
- "A가 아니라 B" 가 측정 가능한 기술 대비인가 빈 수사인가? 기술 대비면 유지.
- 설명과 요약을 새로 쓰나? 등가물을 "X와 동일"로 참조했나(메커니즘 재서술 금지), 핵심(무엇+왜)만 남겼나?
- **문장마다: 이게 없으면 읽는 사람이 다른 결정을 하나? 아니면 삭제.**
- 앞 절이 이미 댄 근거를 다시 대고 있나? 삭제.
- 코드 조건을 산문으로 옮겨 적고 질문에는 답 안 했나? 삭제하고 질문에 답할 것.
- 측정하거나 확인하지 않은 수치를 시나리오, 상한, 범위로 썼나? 삭제.
- "한계 / 주의" 항목마다: 이게 결론을 바꾸나? 아니면 삭제.
- 편집한 내용을 산문으로 다시 설명하고 있나? diff가 말한다, 삭제.
- 줄표(—)로 문장을 이었나? 붙은 절이 필요한지 보고, 마침표나 콜론으로.
- 물결표(~)를 자리 표시나 범위로 썼나? X 또는 "부터/까지"로.
- 한 문장에 괄호 부연이 2개 이상인가? 문장을 나눔.
- 금번, 상기, 명일 같은 문어체 한자어? 일상어로.
